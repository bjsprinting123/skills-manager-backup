# 文档结构与阅读规范

## 目标

正文要同时满足三件事：第一次运行时能照着做；调整参数时能直接理解影响与回退；审计时能追溯每个重要结论的依据。不要用篇幅代替信息密度。

文档首先是 AI 可检索、可追溯的工作底稿：由助手核对节点与证据，用户按需提问，不要求用户逐节点审阅。保留现有十章、参数卡与 Obsidian 格式；把简短结论和下一步放在首页，详证留在相关节点旁。

## 固定十章

1. 工作流简介与适用范围
2. 数据流概览
3. 模型、插件与环境依赖
4. 从加载到运行的操作步骤
5. 全部节点与参数详解
6. 视频讲解与作者说明
7. 原始连接与语义连接
8. 性能、显存与优化建议
9. 常见问题与排错
10. 来源、证据和核验状态

章节存在不代表必须填充虚构内容。没有视频或作者资料时，第六章明确写 `not_provided`，并说明其他章节依据 JSON 与已核实资料生成。

## 首页核验表

至少列出：输入形态、源 JSON 路径、SHA-256、格式/版本、节点与连接覆盖、参数覆盖、节点资料查证覆盖、敏感内容处理、源码或环境基线、运行验证状态。没有实际运行时写“未运行”，不能写性能结论。

## 数据流图

- Mermaid 优先使用从上到下的 `flowchart TB`，避免超宽横图。
- 节点同时显示 canonical type 和中文动作，例如 `KSampler<br/>执行潜空间采样`。
- 先画生成主链，再补控制、提示音、保存或条件分支。
- 图只是概览；物理连线与折叠 Reroute 后的语义连线仍分别列出。

## 因果阶段

按数据依赖组织节点，不按画布横坐标或节点 ID 机械分组。最小文生图常见三段：

1. 采样前准备：模型、文本编码与条件。
2. 生成核心：潜空间与采样。
3. 解码与输出：VAE、保存与完成通知。

图生图、ControlNet、LoRA、局部重绘、视频、音频、多阶段细化或后处理可以增加阶段。章节标题必须解释阶段作用；不要为了维持“三段”把没有直接因果关系的节点塞在一起。

## 5.1 节点导航表

导航表至少包含：ID、节点类型、作用、参数/状态数量、详解位置。

有独立详解的行必须是一键跳转链接。标题和链接必须由同一个字符串变量生成，不允许分别手写。

安全标题模板：

```markdown
#### 节点 ID 4 ModelSamplingAuraFlow 设置采样 shift
```

对应表格链接；表格中的别名分隔符必须转义：

```markdown
[[#节点 ID 4 ModelSamplingAuraFlow 设置采样 shift\|5.3（ID 4）]]
```

标题不得包含反引号或 `# | ^ :`。如果 canonical type 含这些字符，只在标题中把字符替换为空格；表格和正文仍以代码格式写出真实类型。

Reroute 可链接到物理/语义连线章节。没有独立说明的纯画布标签写“本行已说明”，不要创建无效链接。

## 节点参数卡

每个执行节点先写“节点 ID＋canonical type＋中文作用”，再给五列表格：

```markdown
| 参数/状态 | 当前值；源码通用默认；专项官方基线 | 参数作用 | ↑/↓ 或切换分别会怎样 | 本工作流建议、风险与回退 |
|---|---|---|---|---|
| `steps` | 当前 9；源码通用 20；官方模板 8 | 决定去噪更新次数。 | 增加通常更慢且结果改变；减少通常更快但可能欠采样。Turbo 不保证越多越好。 | 先复现 9，再固定 seed 单测 8；异常回退 9。 |
```

要求：

- 标题重复写出 ID、类型和动作，读者滚动到这里仍知道正在看哪个节点。
- 当前值、源码默认、官方专项模板、作者建议、本机实测分栏表达；缺项写 `not_verified`，不要补猜测。
- 数值参数解释增大和减小；枚举参数解释切换的兼容性或行为变化，不强造“正/负方向”。
- seed 数值大小没有质量方向；区分固定 seed 与生成后控制状态。
- 连接输入不是 widget 参数。前端状态、说明文本和执行参数分别标注。
- 长文件名可以在卡片内换行，但不得为了排版修改真实值。
- 建议栏写清适用条件、具体动作、理由、风险、失败退出和证据状态；参见 [设备适配协议](hardware-compatibility.md)。保留原值可以是合理建议，但须说明理由；纯显示状态或不影响当前路径的字段应解释其边界，不强编性能优化。尚未核实的建议明确标记，不能用批量套话冒充完成。

## 模式、弹窗与运行生效层

模式选择不是每个工作流的固定章节。只有 JSON、权威 schema、节点源码或前端实现确实暴露模式/枚举时才写，并按实际数量完整列出；可能是 1、2、3、4 或更多项。

模式表至少说明：控件所在位置、当前选择、全部已证实选项、每项改变的执行路径、不会改变的内容、与下游节点的兼容性、保存/重新排队/重载要求和回退值。无法从证据确认选项时写 `not_verified`，不能把另一个工作流的选项复制过来。

复杂节点常同时存在五层状态，正文必须分开：

1. 外层节点直接控件；
2. 按钮打开的弹窗或嵌套配置；
3. JSON 已保存值；
4. 当前前端会话显示值；
5. 日志与输出证明的运行生效值。

“界面显示”“计划生成”和“实际生成”不得混写。诸如 `display_info`、总时长、分段数和二采状态只能作为计划层证据；日志、输出文件时长和元数据才是运行层证据。

## 素材、提示词、音频与分段调度

涉及图片、视频或音频素材时，分别核对：素材已启用、文件路径存在、节点已重新绑定、提示词引用标签存在、`SCENE_INSTRUCTION`/`AUDIO_INSTRUCTION` 槽位有效、下游解码与合成连接存在。任何一项成立都不能代替其余项。

- `overall_soundscape`：画面内环境声、动作声和整体声场描述，不等同于背景音乐文件。
- `non_diegetic_music`：画面外配乐意图；若要复用用户音频，还需实际音频槽位/连接成立。
- “每段时长 × 生成数量”只是计划总时长；最终时长以成功生成并合并的分段为准。
- 故事扩展、故事拆解、穿透生成、仅提示词输出等名称只在当前节点源码确实存在时使用，并记录空输出对下游解码/保存节点的影响。

## 模型与依赖

- 只把 JSON 实际引用的模型列为当前依赖。
- 作者目录、百科或其他工作流出现的模型只能作为可选扩展。
- 文件名不是 dtype、来源或许可证证据。若检查文件，记录真实路径、大小、SHA-256、张量 dtype 与核验方法。
- 核心节点、自定义节点、UUID 子图实例和未知节点分开标注。

## 节点资料查证在正文中的落位

- 第三章列出每个节点包的归属、保存版本、本机安装状态和官方来源；无法定位时写明确状态，不猜仓库。
- 第五章每个执行节点的作用、参数名、源码默认和兼容性结论必须能追溯到节点查证矩阵。当前值仍只来自当前 JSON。
- 第九章的报错与修复可以引用社区经验，但必须标明来源、版本和适用条件；单个帖子不能写成普遍结论。
- 第十章汇总节点查证覆盖：不同节点类型总数、非执行辅助类型数、已有本机/官方依据数、社区检索数、未解决数及证据路径。
- 视频或作者说明只解释作者的用法，不能替代官方/源码核验。官方、作者、社区和本机实测冲突时并列呈现，并说明正文采用哪一项及原因。

## 连接章节

- 先解释 Node ID 与 Link ID 是两套独立标识。高编号通常来自画布创建、复制、删除和重新连接的历史，不代表执行顺序、优先级或节点数量。
- 物理连线表保留 canonical 节点类型、接口名和数据类型，同时在同一格给出中文动作与对象解释；不要让读者只面对 `MODEL`、`CLIP`、`CONDITIONING`、`LATENT`、`VAE`、`IMAGE` 等英文类型。
- 每条重要连线说明传递什么、服务哪个阶段，以及断开或接反时的直接后果。
- 语义连接按真实数据依赖重新讲成可读步骤。即使没有 Reroute、物理与语义连接数量相同，也必须说明执行链，不能只写“与上表相同”。
- ID 只用于追踪；执行顺序由数据依赖决定。除非源格式明确提供，不能从编号大小推断创建时间的具体操作或运行先后。

## 作者原文与视频

- 作者原文可完整保存在证据目录；正文可以原样引用或可读整理，但旁边必须有核验注释。
- 视频要区分平台字幕、本地 ASR 和人工校订。记录视频 ID、访问状态和真实可用时间段。
- 无法访问、需要登录、没有字幕或只拿到摘要时，明确写状态，不能声称已观看或采集完整内容。

## 性能和优化

- 没有本机 A/B 时，只写测试方法、可能性与回退，不写固定提速、显存或画质结论。
- 所有比较先固定输入、seed 与无关参数，并记录模型哈希、软件版本、后端、分辨率、步数、耗时、峰值资源和输出。
- 大型通用性能表进入独立台账；正文只保留与当前工作流直接相关的结论。
- 设备适配、后端替换和分阶段测试按 [设备适配协议](hardware-compatibility.md) 执行。兼容性矩阵放第三章，具体参数建议放第五章，负载与测试顺序放第八章，失败退出放第九章，证据日期与未测项放第十章；用链接复用证据，不新增另一套百科。

## Obsidian 显示

每篇候选文档的第一行必须是 YAML frontmatter，并声明：

```yaml
---
cssclasses:
  - comfyui-workflow-doc
---
```

Markdown 源保持可移植。`assets/obsidian-workflow-docs.css` 负责：

- 宽屏响应式正文；
- 普通表格保持表格，并固定在正文宽度内；长模型名、路径和哈希必须换行，不依赖横向拖动；
- 首列为代码参数且有五列的表格转为两列卡片；
- 窄屏卡片转单列；
- 不依赖横向拖动阅读参数；
- Mermaid 和图片限制在可视宽度。

候选版交付前必须打开**该候选文件本身**的 Obsidian 阅读视图，而不是只在代码编辑器或通用 Markdown 预览里检查。视觉验收同时满足：正文采用宽屏布局；Mermaid 已渲染为 SVG 且节点动作具有中文；五字段参数表已变成两列卡片；参数卡和普通表格都不需要横向拖动；长模型名、路径和哈希在单元格内换行。只检查 Markdown 源码不算完成。

一行或少量字段的状态表不得被 CSS 强制拉成高大的卡片；只把真正的五字段参数解释表转为卡片。普通四列表、路径表和素材状态表保持紧凑。

安装或修改 CSS 属于外部配置变更，必须得到用户授权。
