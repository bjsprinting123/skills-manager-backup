# 设备适配、建议与分阶段测试

在已知目标设备、询问 AMD/CUDA 兼容性、提供加速参考或准备测试时使用。此协议规范取证与决策，不内置某台设备的“最佳参数”。不扩大安装、改环境、改工作流或运行授权。

## 1. 先锁定设备与证据日期

优先读取项目已有设备记录，低风险可核验项再只读刷新：GPU 型号/架构与显存、CPU/RAM、操作系统、目标 ComfyUI 和 Python 路径、版本、驱动/计算栈、后端。每项记录来源与日期；服务不可用时保留最近快照并标为历史，不自动启动或循环查询。

Windows AMD、Linux/WSL ROCm、NVIDIA CUDA 分开讨论，RDNA 代际也不能混用。PyTorch 的 `torch.cuda`、`cuda:0` 可以是 HIP 接口名称，不能据此判 NVIDIA-only。页面文件不是显存，也不是不发生 OOM 的保证。

## 2. 沿实际执行链逐层核验

矩阵以节点路径（根图/子图/实例）、canonical type、版本、保存模式与连线为锚点，逐项记录下列层次；未知项保留 not_verified，不以其他层次代替：

| 层次 | 所需证据 | 不能推出的结论 |
|---|---|---|
| 引用与可用性 | 精确模型选择、实际文件路径、节点注册、依赖清单 | 作者有源码不等于本机安装；索引 missing 不等于文件缺失 |
| 实现兼容性 | 当前节点调用链、输入类型、模型族/张量格式、attention hook、原生扩展及后端限制 | 读到通用 PyTorch 调用不等于所有内核均可用 |
| 后端与加载 | 目标 Python 包版本、DLL/接口存在性，再按授权取得导入/加载日志 | HIP DLL 存在不等于 DLL 已加载；导入成功不等于特定权重可推理 |
| 执行与输出 | 实际提交 API Prompt、有效参数、分阶段日志、可读取的输出文件 | 界面无缺失项或日志完成不等于结果有效 |
| 性能与稳定性 | 固定条件的对照测量、重复次数、资源峰值、输出质量 | 单次成功不等于最快、长期稳定或普适 |

已发现硬限制须给精确实现依据和适用版本；否则结论写“所查路径未发现硬性限制，仍有这些待测项”，不写“没有任何不兼容节点”。每条检查明确覆盖范围和非执行分支；旁路/停用状态、内外层值、前端转换与实际 API Prompt 分开。

独立 LLM（例如 llama.cpp）与扩散模型 PyTorch 链分开：改变后者的注意力节点不能修复前者的加载器。文件名中的 FP8/MXFP8/NVFP4 既不能证明内部格式，也不能单独决定 AMD 可用性；核对元数据、张量类型、加载实现及实际版本。

## 3. 将证据变成可选建议

运行之前即可给建议，但明确写“设备/源码推导，未实测”。在参数卡内写：当前有效值的依据 → 适用条件 → 具体候选值或动作 → 理由 → 风险 → 如何退出失败路径。无依据的候选值不填数字，写缺少哪项证据。

- 优先处理实际负载因素：分辨率、批量、驻留/卸载、上下文、量化与可选后处理；不把减少步数当作所有 OOM 的修复。
- 被连线或外层代理覆盖的控件，要定位真正生效入口。关闭分支只解释再启用时的影响，不列为当前必调/必下载。
- 像素或帧数比例可计算，但不能直接折算成显存或耗时收益。分块仅针对支持该控件的编解码阶段，不能声称能修复其他阶段。
- 区分“恢复作者原配置”和“失败后恢复可用状态”。原配置本身若未跑通或更耗资源，不应作为 OOM 的安全退出；优先保留已成功输出、停用失败分支。
- 固定非性能字段可以是正确选择，说明用途和保留理由；尚未核实写明状态，不能用“保存原值，异常回退”填满建议栏。

## 4. 复用加速案例的边界

参考案例至少保留：源工作流路径/哈希、模型族、设备/系统/后端版本、启用与停用节点、输入输出类型、补丁顺序、内外层覆盖、证据等级及实际测试状态。

提出替换前核对目标模型的 hook、张量布局/dtype、补丁冲突、原生内核与回退路径。后端选项存在或函数缺失时可回退，不代表运行时内核报错也被捕获。参考图中关闭的 Sage/BlockSwap 不得变成默认建议；也不跨模型族搬运专用权重、LoRA 或 VAE。

案例留在本次证据包；获得正式发布授权后，节点机制归现有节点详解，图中特定配方归现有应用指南，可复用模型身份归模型库 Skill 统一发布入口，真实测量归性能台账。未运行的推导不写成实测，模型卡缺失仍按原交接协议处理，不互相递归调用。

## 5. 把测试准备与执行分开

若用户说“先更新文档，之后测试”，本次只准备清单。每阶段写明：前置条件、测试分支与节点、唯一变量（或明确成组因素）、成功标准、失败停止点、需留存证据；运行状态保持 not_performed。

通常顺序是只读预检 → 最小生成核心 → 独立提示词/媒体组件 → 重新接入原链 → 一个可选后处理 → 必要时另一个分支。依据真实图调整，不强制所有工作流有这些阶段。

隔离组件时先检查接口类型和前端展开。以固定文本替代 LLM 输出是一种降功能测试副本，不是旁路模型加载器就能接出文本；通过基础链不代表原完整链通过。仅在取得修改/运行授权后创建并执行副本，不覆写源文件。

实际测试保留工作流/API Prompt 哈希、权重身份、软件/后端版本、有效 seed、尺寸/批量、日志、输出及测量方式。失败先定位最后异常与阶段；停止失败分支，不连续换多个包、模型和后端掩盖原因。结论按“该阶段/该配置通过”报告，完整链须单独验证。

## 6. 交付检查

助手检查硬件来源、当前值、推荐依据、作用路径、已知阻碍与待测项是否一一对应，并给出四个独立状态：结构、视觉、语义、运行。现有脚本结构通过不等于本协议已自动检查；语义核验用可定位的证据逐项复核。用户只需决定目标、取舍和发布，不负责逐节点查错。
