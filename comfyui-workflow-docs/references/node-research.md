# 节点资料查证协议

## 目的与顺序

节点查证必须发生在 JSON 初步解析之后、候选文档撰写之前。先解析是为了取得精确的 canonical type、节点包、保存版本、当前参数和连接；若先按显示名称盲搜，容易把同名节点、其他包的实现或新版说明套到当前工作流。

固定顺序：

1. 从 JSON 生成不同节点类型的查证任务清单；Reroute、标签和说明节点标为非执行辅助类型。
2. 用当前环境的 `/object_info`、节点源码或包清单确认字段、默认值、输入输出和版本。
3. 打开官方文档、官方仓库、发布说明或模型卡确认用途、安装、兼容性和专项基线。
4. 对自定义、未知、缺失、版本冲突或行为敏感节点做针对性社区检索，补充常见报错和使用边界。
5. 将作者视频、社区经验和本机实测分别写入矩阵，不与官方事实合并。
6. 矩阵覆盖完成或每个缺口都记录明确状态后，才能起草候选文档。

## 分层要求

| 节点类别 | 最低查证要求 | 社区检索要求 |
|---|---|---|
| ComfyUI 核心普通节点 | JSON＋当前核心源码或 `/object_info`；涉及专项模型时再核对官方模板/文档 | 仅在正文要写兼容性、排错、性能或争议行为时需要 |
| 自定义节点 | JSON＋包归属＋当前源码/schema＋官方仓库或官方文档 | 必须做针对性检索；没有可靠结果也要记录状态 |
| 未知、缺失或包归属冲突节点 | JSON 原值保留；搜索官方注册表、仓库和当前环境 | 必须检索，并保留 `unavailable`、`not_verified` 或冲突说明 |
| UUID 子图实例 | 先展开 definitions，内部节点逐类型查证 | 按内部节点类别执行，不能只查子图显示名 |
| 纯 Reroute、标签和说明节点 | 确认其不执行生成逻辑及连接作用 | 通常不需要社区检索 |

社区检索不是投票。GitHub Issues、Civitai、LiblibAI、论坛或视频评论只能作为经验和线索，不能覆盖当前 JSON、当前源码或官方资料。

## 固定产物

机器解析后创建；清单覆盖全部不同节点类型，非执行辅助类型仍保留但不强制社区检索：

```text
02-机器解析/03-节点查证任务清单.json
```

至少包含每个不同可执行节点类型的：

```json
{
  "node_type": "KSampler",
  "node_ids": [13],
  "package_hint": "comfy-core",
  "saved_versions": ["0.34.2"],
  "research_class": "core",
  "required_checks": ["local_schema", "official_source"],
  "status": "pending"
}
```

启用外部研究时创建：

```text
<外部查证目录>/节点资料查证矩阵.json
<外部查证目录>/节点资料查证矩阵.md
<外部查证目录>/raw/              # 搜索与页面抽取原始结果
```

矩阵每行至少记录：

- canonical node type、涉及的节点 ID、包和保存版本；
- JSON 当前事实；
- 本机 schema/源码状态及路径或 commit；
- 官方来源 URL、访问状态和支持的具体结论；
- 社区检索查询、来源 URL、访问状态和适用边界；
- 作者视频时间码（如果有）；
- 本机实测状态；
- 冲突、未解析项和正文采用口径。

## 来源状态与完成条件

允许的来源状态：`obtained`、`not_provided`、`unavailable`、`login_required`、`insufficient_evidence`、`not_verified`。

搜索摘要只用于发现链接。只有实际打开并读取原页面，才可把页面记为 `obtained`。需要登录而没有授权时记录 `login_required`，不能用相似页面代替。

节点查证完成不等于所有来源都有结果。完成条件是：

1. 任务清单覆盖全部不同节点类型，并单独标识非执行辅助类型。
2. 每个节点类型至少有一项可追溯的实现依据，或明确记录无法取得依据。
3. 每个自定义、未知、缺失或冲突节点都有官方发现记录和社区检索记录。
4. 当前值、源码默认、官方专项基线、作者建议、社区经验和本机实测没有混写。
5. 文档中的确定性结论能指回矩阵中的具体证据；证据不足的内容写为待核实。
