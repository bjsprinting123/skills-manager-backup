# 输出与文件整理

## 最小交付

- `inventory.json`：逐文件快照，扫描方式、路径、大小、mtime、结构提示、哈希与异常；完整路径覆盖，不把分片数说成模型数。
- `模型库说明.md`：角色速查、每个模型的中文卡、可核实搭配、选择建议、未知项和来源。资料多时按家族分文件并提供索引。
- `catalog.json`：与说明一致的机器可读卡片，供后续更新/改名复用。已有可靠目录可沿用其格式；新建可用下列结构。
- `research_tasks.json`：使用 `catalog_tools.py prepare` 时生成的逐文件待查清单。准备脚本同时生成中文草稿；未查证的草稿不等于完成报告。
- 用户需要改名/去重时再生成 `rename_plan.json`、`重命名对照表.md`，执行后增加操作日志和结果核验。
- 工作流交接或用户要求维护共享库时，另生成 contribution 候选；只有明确授权发布后，才由 `shared_model_library.py` 写入共享索引、不可变 revision、`模型卡.md` 和 `评论参考.md`。格式和冲突规则见 [共享模型资料库与工作流交接](shared-library-handoff.md)。

单张卡建议字段（无法核实填明确未知原因，不补猜测）：

`catalog_tools.py` 使用外层对象 `{"schema_version": 1, "inventory_sha256": "输入 inventory.json 的完整 SHA256", "cards": [...]}`，`cards` 中各条沿用下列字段。其他已有格式可先显式转换，不能删除快照绑定后声称通过本工具校验。

```json
{
  "files": ["相对盘点根目录的路径"],
  "identity": {"status": "verified|partial|unknown", "sha256": null, "publisher": "", "version": "", "remote_file": ""},
  "role": "加速 LoRA 等；未核实需注明",
  "one_sentence": "不用术语也能理解的一句话用途",
  "use_when": "什么时候选它",
  "compatibility": {"base": "", "task": "", "encoder_vae": "", "loader": ""},
  "name_parts": {"片段": "含义及依据"},
  "usage": {"trigger": "未提供/不适用/实际触发词", "weight": "", "steps": "", "scheduler_cfg_shift": ""},
  "acceleration": {"kind": "none|few_step_adapter|distilled_base|quantization|runtime|unknown", "benefit": "", "tradeoff": ""},
  "limitations": [],
  "sources": [{"url": "", "publisher": "", "version_or_revision": "", "checked_at": "", "file_sha256": "身份核验时填写发布记录中的完整文件哈希", "supports": ["identity", "purpose"]}],
  "tested": {"load": false, "generation": false, "performance": false},
  "suggested_name": "保留原始 ID 并附中文用途"
}
```

`verified` 必须有完整本地 SHA256 与可靠发布记录一致的证据。没有哈希时即使用途资料充足，身份仍可为 `partial`。另列每个关键字段的依据；不能用一个总体状态掩盖未知兼容性。针对分片，保留每个文件并读取 index 的 weight_map 确定逻辑模型；不要单独改分片名。

共享资料卡还必须把 `model_role` 与 `artifact_form`、网页身份状态与本地绑定状态分开。社区反馈逐条保存立场、主张、参数上下文、环境、来源、核查时间和验证状态，不汇总成伪精确分数。`用户选择.md` 不属于研究 contribution，发布器永不创建、覆盖或删除它。

交付前验证：每个清单路径被且仅被一张卡覆盖；card.files 不出现清单外路径；重复共享卡需有对应证据；每个“已核实”的 SHA256 在存档来源可定位。分开报告内容覆盖与验证覆盖。

`catalog_tools.py validate` 自动检查快照绑定、路径覆盖、共享卡哈希及 `verified` 的必要来源字段。它不能验证网页是否真的包含该哈希，也不把来源字段齐全视为所有用途、兼容性和加速效果均已证明。填写完目录后先校验，再 `render` 到新的 Markdown 文件，人工检查内容与引用；脚本不会覆盖原有说明。

## 中文命名方案

推荐：`角色-原模型ID及版本-关键任务或用途-必要精度标记.原扩展名`。

- 让用户看到用途，同时保留上游可搜索的模型 ID、版本、分支、格式标记。多写描述不等于把整张说明卡塞进文件名；通常保留最有区分力的两项用途即可。
- 未确认的用途不写成肯定标签；可加“用途待核实”，或先保持原名。不得从角色罗马音猜触发词、从 NSFW 猜油画、从文件名 D 猜 3D。
- 避免 Windows 非法字符、尾随点/空格、保留设备名和大小写碰撞；兼顾应用路径长度。扩展名不变。
- 检查配套侧车文件、分片索引和配置引用。路径绑定的复杂包优先通过说明卡或目录索引增加可读性，不能贸然单文件改名。

## 去重和执行

用户要减少库存时，先区分内容去重与用途精简。内容去重按下面的SHA流程；用途精简按 [保留与替换建议](review-and-recommendations.md#保留与替换建议)给出具体文件、接受的损失、把握和引用影响。没有相同SHA不等于只能建议全部保留；候选建议也不等于已经获准删除。

1. 按大小找候选，然后对候选全文件计算 SHA256。`same_size_candidates` 绝不是删除清单。确认文件在读取期间没有变化。硬链接、快捷方式、junction 与独立文件分别处理；扫描脚本跳过目录链接，但普通硬链接可能仍计入多个路径，释放空间不能简单相加。
2. 同哈希组选择保留位置时考虑已有工作流引用、家族组织和作者名。不同格式、任务、精度、版本、rank 或不同哈希不能按内容重复自动删除；用途取舍另列依据。来源未知不作为垃圾文件判据。
3. 形成具体计划：每项旧/新绝对路径、完整哈希、大小、保留副本、理由、相关侧车文件、引用影响。先按 SHA256 查指定资料库，记录关联 model_id、当前 revision、local_files、别名和未入库项；将需要修复的当前绑定加入同一计划。检查目标冲突，不覆盖已有文件。用户已经授权当前范围的改名/去重时继续执行；只有实质新增范围或不能安全决定的破坏性选择才询问。
4. 重命名会影响工作流中的模型选择。只在已指定/已知工作流范围内查引用，记录找到的引用及未检查范围。修改 JSON 需核实节点字段语义，不能盲猜 widgets_values 索引或替换提示词、URLs；是否更新工作流按用户授权处理。
5. 执行前再查源文件状态与保留副本。Windows 用单一 PowerShell 的 LiteralPath 操作，解析绝对路径并确认仍在授权根目录内；不递归删除推算出来的目录，不跨 shell 拼接删除命令。
6. 留下已完成操作日志；改名保留反向映射，删除说明保留副本及恢复原路径的方法。按 [文件整理后的资料同步](shared-library-handoff.md#文件整理后的资料同步) 发布关联资料库的当前绑定，保留旧名为别名、旧 revision 为历史。后验检查文件数量、内容身份、当前工作流字段、资料库 local_files 与 revision，保存发布回执及查询验证。失败后依据日志继续，不重复执行已完成项。

不自动下载替换模型、不批量更新节点、不运行长时间生成。用户要求实测时再进行最小可验证的加载/生成测试，明确费用与运行环境约束。普通报告完成不等于共享库已发布；分别报告候选、校验、授权、发布和工作流回填状态。
