# 身份、用途和搭配的研究规范

## 证据链

每项结论区分依据：`本地结构`、`作者说明`、`实现代码`、`社区经验`、`推断`、`本机实测`、`未知`。身份已核实不代表效果、兼容性、速度都已经核实。

推荐顺序：

1. 读取路径、大小、文件头；查看相邻模型卡或下载记录时只提取有关模型的字段，保护凭据和私人提示词。
2. 对需要确认身份或重复的文件计算完整 SHA256。与作者/发布方的文件哈希对比；保存来源 URL、检索日期、仓库 revision 或精确版本 ID、远端文件名、哈希字段及本地对应路径。HF 可用仓库 API 的 LFS SHA256；Git commit、ETag、短哈希和普通 Git blob SHA1 不等于完整权重 SHA256。
3. 检查该版本模型卡、官方文档、作者社区帖子、节点源码和示例工作流。哈希相同只证明字节相同；不同哈希也可能仅元数据不同，但不能据此自动删除。
4. 没有哈希来源时交叉验证张量结构、元数据、文件名、大小和发布记录，标为“部分核实”；搜不到标为“待核实”。不要将搜索摘要当作完整使用说明。网页无法访问时记录缺口，并继续处理能查到的项目。
5. 引用与具体结论邻近。社区反馈标明版本和环境；不把作者宣传速度当作用户机器上的结果。

身份记录分开保存发布者账号、发布页标题、精确版本、原下载文件名、本地文件名及SHA。标题不是作者账号；标题与文件名不同不是两件模型；“来源页见sources”不能代替已能查到的原文件名。以发布记录和文件SHA证明对应，不能仅因两个名称指向同一张自建卡就反推它们相同。

读到模板README而没有参数时，继续检查该发布页实际承载说明的字段（如ModelScope模型详情Description）。参数、搭配对象和版本后缀按精确说明解释；“作者列了训练词”“作者要求必填触发词”“作者明确说可不加”分别记录。明确点名的搭档写成精确模型/文件，不简写成“另一张同作者LoRA”。

## 社区使用反馈

联网前先查共享库中精确身份、来源版本和核查日期。身份、版本、节点行为不一致或资料缺失时定向检索；同一任务复用已打开的来源证据。登录受限、限流或连续失败时记录来源状态并继续可完成的部分，避免无限重试。保留每次检索词、来源 URL、核查时间与支持字段，不把重新访问网页等同于本机验证。网页新版本与旧结论冲突时保留版本边界和双方证据。

用户要求参考网上评论时，查找可打开并可定位原文的实际使用记录；搜索摘要只作为找来源的线索。每条反馈记录倾向、主张转述、参数上下文、硬件/软件环境、来源 URL、核查时间和核验状态。版本、底模、节点、参数或环境未说明时逐项写“未说明”，不要补猜。

允许收录尚未独立验证的评论，但必须与作者说明、本机实测和用户选择分开。保留有信息量的正面、负面和混合反馈，不能只挑支持既有结论的内容；几条评论不能写成社区共识，点赞数和发布者声望也不证明参数正确。不要自动生成综合推荐分。主要使用转述；直接摘录遵守 [共享模型资料库与工作流交接](shared-library-handoff.md) 的短摘录限制。

报告渠道覆盖时，列出实际页面、证据类型、读到的内容、采纳与不采纳的理由、未取得的部分。作者发布页、转载页、平台对照和独立用户评测分别计数；多个网站转载同一说明不算多份独立验证。根据当前文件来源和任务选择渠道，不固定追求站点数量。单次访问失败只说明该次该页未读到；新证据推翻旧渠道结论时，同时更新当前入口，保留历史存档的日期。

基础事实不要依赖目录位置：扫描脚本的 `directory_hint` 仅说明放置位置；`adapter_markers` 只说明出现适配器结构，不区分角色、风格或蒸馏。文件头 dtype 是存储信息，不足以确定计算精度、量化算法或运行速度。GGUF 扫描仅验证最小头部，详细量化类型需要专用读取器/发布说明。

## 面向初学者的分类

| 角色 | 应解释的问题 |
| --- | --- |
| 完整 checkpoint / 扩散主模型 | 负责生成什么？完整整包还是需要另外配编码器和 VAE？ |
| 风格 / 角色 / 概念 LoRA 或 LoKr | 改画风、人物还是细节？哪些底模兼容？是否有触发词？ |
| 编辑适配器 | 是风格影响还是图像条件编辑？是否需要专用节点和输入图？ |
| 加速 LoRA | 为哪个任务和底模蒸馏？对应几步、哪个噪声分支？ |
| 文本 / 视觉 / 音频编码器 | 把哪种输入转换成模型能理解的条件？不是独立出图模型。 |
| VAE / 音视频编解码器 | 把潜空间转成图片、视频还是声音？必须匹配哪个模型？ |
| ControlNet / model patch | 接收什么控制条件？走哪个加载节点？是不是仅供某个底模版本？ |
| 放大 / 插帧模型 | 处理最终像素还是潜空间？适合图片、视频还是音频？ |
| 检测 / 分割 / 姿态估计器 | 生成控制信号还是直接生成内容？ |
| LLM / 投影器 / embedding | 是提示词助手、视觉投影还是文本概念向量？需要哪个宿主？ |

说明主模型 ↔ 编码器 ↔ VAE ↔ 适配器 ↔ 加载节点的兼容关系。每条关联给依据或“待核实”，不能因为文件位于同名子目录就画实线搭配。另行标明模型角色和制品形态；分片文件的单片哈希不是整套模型的哈希，没有 manifest/composite 依据不能认证完整制品。

## 加速与名称解读

| 类别 | 可合理解释的作用 | 必须查清的条件 |
| --- | --- | --- |
| 少步数蒸馏 LoRA | 在配套模型和采样方案下减少推理步骤 | 任务分支、底模版本、NFE/steps、调度器、CFG、视频/音频 shift、权重、画质代价 |
| Turbo / Lightning 等主模型 | 主权重可能已包含蒸馏能力 | 是否还需要额外适配器；不要只看 Turbo 一词就叠加加速 LoRA |
| FP8 / INT8 / INT4 / GGUF 量化 | 降低存储成本，可能降低显存需求 | 实际算法、加载节点、GPU/内核支持、运行转换成本、质量变化；文件大小不等于峰值显存 |
| 编译 / 注意力内核 / 缓存 | 优化执行过程 | 节点实现、硬件、首次编译成本、缓存误差；与模型文件分开 |
| 分块 / 卸载 | 减轻显存压力 | 可能增加时间，不能标成无条件提速 |

逐段解释原文件名，保留有辨识度的原模型 ID：模型家族、任务、版本、训练分辨率、少步数标记、rank、精度、量化、格式。`step00004000` 可能是训练检查点，不能叫“4000 步加速”；`rank_24` 不是强度 0.24；`768p` 若是训练分辨率就不能说是强制输出尺寸；`comfyui` 可能是张量键转换版本而非更高画质。每项均以对应发布版本说明确认。

有硬件和工作流信息时才给实际性能比较。记录 GPU、显存、分辨率、帧数、模型精度、节点版本、采样步数、冷/热运行、总时长与峰值显存；缺少实测时只提出验证办法，不给虚构百分比。
